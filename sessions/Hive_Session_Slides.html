Asking questions of

Apache Hive lets you ask ordinary SQL questions of data far larger than a spreadsheet — without learning anything new if you've seen SQL before. Case study: analysing a 200,000-line web server log.

Where we are

Last time the spreadsheet broke. Today: a friendlier fix.

When data got too big, we met Pig — a team of machines splitting the work. Pig is powerful, but it's a step-by-step scripting language. Today's tool asks for the answer a different way.

The good news for this roomHive speaks SQL. If you've ever written SELECT … WHERE …, you already know most of Hive. You describe what you want, not the steps to get it.
The everyday twin

Hive = SQL for a warehouse of files

Think of a normal database as a filing cabinet where everything was carefully typed in and sorted. Hive is different: you point it at a pile of files you already have — and it lets you ask them database questions.

Built by

Facebook, to let analysts query Hadoop without writing Java. Now an Apache project.

The language

HiveQL — SQL with tiny differences. Tables, rows, columns, SELECT, JOIN, GROUP BY.

Underneath

Hive turns your SQL into a big-data job (MapReduce / Tez / Spark) and runs it across the files.

The one idea that makes Hive click

You don't load the data. You label it.

Normal database — “schema on write”

Before you can ask anything, you must re-type all the data into the database in its exact format. Slow, and you fix the shape up front.

Like emptying every document into a new cabinet, retyped and sorted, before you're allowed to look.

Hive — “schema on read”

The files already exist. You just lay a table shape on top of them and start asking. Nothing is copied or reloaded.

Like sticking labelled tabs onto a filing cabinet you already own — instantly searchable, nothing retyped.
Say it once, remember it all sessionHive attaches a table shape to files that already exist. The data stays put; Hive holds only the description — like a table of contents, not the book.

A common confusion

“Isn't this just a database?” — no

 Normal database (RDBMS)Hive
SchemaOn write — shape before loadingOn read — shape files that exist
ScaleTerabytesPetabytes
PatternRead & write constantly, liveWrite once, read many times

Hive is a data warehouse for analysis, not a live transaction system. It answers big questions over history — not “what's in cart #7 right now.”
Under the hood · detail

Hive's architecture, in plain parts

Clients — how you connect

CLI (command line), Web UI, and JDBC / ODBC / Thrift drivers so tools like Tableau or a Java app can talk to Hive.

Metastore — the catalogue

Remembers every table's shape: names, columns, types, and where the files live. The description only — never the data.

Driver → Compiler → Engine

The Driver takes your query, the Compiler turns it into a plan, the Execution Engine runs that plan over Hadoop.

Most work uses just STRING, INT, and DOUBLE. The complex types (ARRAY, MAP, STRUCT) are how Hive handles the semi-structured data from Session 1 — a column that holds a little list or record inside each row.
Reference · two kinds of table

Managed vs. external tables — a safety point

Managed table

Hive owns the data. Drop the table and Hive deletes the files too.

Use for data Hive itself created.

External table (what we use)

Hive only points at files it doesn't own. Drop the table and the files stay safe.

Use for company data that already exists — like our log.

In the lab 
CREATE EXTERNAL TABLE access_logs ( ip STRING, status INT, … )
LOCATION '/content/logdata';   -- points at files; never copies them
Reference · making big tables fast

Partitions & buckets — Hive's speed tricks

Partition — separate drawers

Split the table by a column, e.g. by date. A query for “11 Oct” reads only that drawer — not the whole year.

Like filing invoices in one folder per month — you open October, not the whole cabinet.

Bucket — fixed sub-bins

Inside a partition, spread rows into a fixed number of files by a column (e.g. customer id) so lookups and joins land in the right bin fast.

Like A–Z dividers inside the October folder.
Why a manager caresPartitioning is the difference between a report that scans one day and one that scans five years — same query, a fraction of the cost and wait.

The business case

Why companies run Hive

  • Reporting at scale. Analysts answer questions over years of data in the SQL they already know — no engineer needed for every request.
  • Cheaper questions. When a query is two lines of SQL, people ask more of them — and decide on evidence, not instinct.
  • Keep everything. Reading files as-is means a company can analyse its whole history, not just the sample it had room to load.
  • Familiar tools plug in. Tableau, Power BI and Excel connect to Hive over ODBC — the warehouse feels like a database to the people using it.
Manager's readHive turns “that would take an engineer a week” into “an analyst can answer that this afternoon.”
The takeaway

The SQL you know.
Files you couldn't open.

Hive answers everyday database questions over data far too big for a spreadsheet — by labelling files instead of reloading them. The six queries you'll run today would work unchanged over billions of rows on a real cluster. Only the scale changes.
