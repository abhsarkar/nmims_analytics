Block 1 · SQOOP

SQOOP

The simplest of the three. One job: move data in bulk between a regular database and Hadoop.

SQOOP · the everyday twin

The moving van between two buildings

Your company's day-to-day data lives in a normal database — the "old office." Hadoop is the big new "warehouse" for analysis. SQOOP is the moving van that shuttles boxes between them.
Company databaseMySQL, Oracle, SQL Server
⇄
SQOOPthe moving van
⇄
HadoopHDFS / Hive
The nameSQOOP = SQL + Hadoop. It literally bridges the SQL world and the Hadoop world. That's the whole tool in its name.
SQOOP · what it does

Two directions, that's it

Import

Database → Hadoop

Pull existing business data into Hadoop so you can analyse it with Hive. The common case.

Export

Hadoop → Database

Push results back into a database so dashboards and apps can use them.

what a command looks like — you will never write this 
sqoop import --connect jdbc:mysql://.../sales --table orders --target-dir /hadoop/orders
One idea to keepBulk transfer, both directions. Nothing more. It is plumbing.
SQOOP · under the hood

The van doesn't have one driver — it has a team

Imagine the moving van doesn't load boxes one-by-one. It sends four workers into the building at once, each assigned a different floor. They load in parallel and the van fills four times faster.

This is why SQOOP can move millions of rows in minutes — it splits the work across parallel workers (called mappers), each reading a slice of the table at the same time.

JDBC connector

The loading dock

SQOOP connects to the database using JDBC — the same standard connector that every Java app uses. Any SQL database with a JDBC driver works.

Mappers (default 4)

The parallel loaders

Each mapper reads a range of rows (split by a column, usually the primary key). More mappers = faster, but more load on the source database.

File formats

How the boxes are packed

Data lands in Hadoop as text, Avro, or Parquet. Parquet (columnar) is compact and fast for Hive queries later.

₹ Why the CFO caresIncremental import — only the new or changed rows, not the entire table — cuts transfer time and database load dramatically. The van doesn't haul the entire building every night, just what is new since yesterday.
SQOOP · who uses it & why

The nightly bulk load

  • A bank's transactions sit in an Oracle database all day, running the business.
  • Every night, SQOOP copies the day's data into Hadoop in one big batch.
  • Analysts then run Hive over months of that data — fraud patterns, spending trends.
  • The live database stays fast (it is not being queried for analysis); Hadoop does the heavy thinking.
◆ Discuss
Why move the data at all — why not just run the big analysis on the live database directly?
SQOOP · when to reach for it

Reach for SQOOP when…

  • You need to move a large batch of data between a database and Hadoop.
  • It is periodic, not constant — a nightly or hourly job, not a live feed.
  • The data already lives in a structured SQL database.
Honest, worth knowingSQOOP is the classic tool for this and is still widely taught. Modern data pipelines increasingly use streaming or newer transfer tools — but the idea (bulk bridge between SQL and Hadoop) is what matters, and it is everywhere.
Block 2 · Kafka

Kafka

For data that never stops arriving — a live stream of events flowing in real time.

Kafka · the everyday twin

A conveyor belt that never stops

Producers drop items on one end of a belt; consumers pick them off the other end — continuously, without anyone waiting. Or think of a newspaper subscription: publishers publish, subscribers receive, nobody phones ahead.
Producersapps sending events
→
Kafkathe belt / the feed
→
Consumersapps reacting to events
The mental shiftStop thinking "a file of data." Start thinking "a never-ending flow of little events" — each click, order, or sensor reading, the instant it happens.
Kafka · the belt has lanes and bookmarks

Topics, partitions, and offsets

The belt is not one long strip — it is split into parallel lanes. Orders go on one belt, payments on another. Within each belt, every reader keeps a personal bookmark so it knows exactly where it left off.

Topic

A named belt

A category of events. QuickKart might have topics called orders, payments, deliveries. Each is an independent stream.

Partition

A lane on the belt

One topic splits into parallel lanes. More partitions = more throughput. Events within a partition stay in strict order.

Offset

A bookmark

Each consumer tracks its position on the belt. Crash and restart? It picks up exactly where it stopped — nothing missed, nothing double-counted.

₹ Why the CFO caresPartitions are Kafka's scaling knob. 3 partitions = 3 consumers working in parallel. Need to handle 10× the festive-night load? Add more partitions, add more consumers. The belt gets wider, not longer.
Kafka · the belt has a memory

Retention, replay, and consumer groups

Unlike a real conveyor belt, Kafka keeps items on the belt even after someone picks them up. Think of the newspaper archive: today's readers get today's edition, but a new team member can still read last week's papers.

Retention

The archive window

Kafka keeps messages for a configurable period — typically 7 days. After that, old messages are deleted to free space. Some companies keep weeks or months.

Replay

Rewind the bookmark

Reset a consumer's offset to re-read old events. Bug corrupted last Thursday's processing? Rewind and reprocess — the data is still on the belt.

Consumer group

A team of workers

Five inventory servers form a group: Kafka assigns each a partition. One dies? The others take its lane automatically. The group reads every message exactly once.

The manager's safety netRetention + replay means mistakes are recoverable. A batch job that ran wrong can be re-run over the same data. That's insurance you don't get with a system that discards events the instant they're read.
Kafka · the key contrast

Batch vs. stream — the whole difference

SQOOP — batch

A van trip, now and then

Move a big load once a night. The data sits, then moves in bulk, then sits again.

Kafka — stream

A belt that never stops

Data flows continuously, event by event, the moment each one happens. No waiting, no batch.

Say it out loudSQOOP moves data occasionally, in bulk. Kafka moves it constantly, one event at a time. Same goal — get data from A to B — completely different rhythm.
Kafka · who uses it & why

Anything that happens "live"

  • Uber — every ride request, driver location, and price update, streaming in real time.
  • Banks — every card swipe checked for fraud the instant it happens.
  • QuickKart on festive night — orders flooding in nonstop; each one needs to hit inventory, delivery, fraud, and dashboards immediately.
  • LinkedIn (who built Kafka) — every profile view and click in your activity feed.
◆ Discuss
On festive night, orders never pause. Why would collecting them in a nightly batch (SQOOP-style) be a disaster here?
Kafka · when to reach for it

Reach for Kafka when…

  • Data arrives continuously and you cannot wait for a batch.
  • Many different systems need the same live feed at once (inventory, delivery, fraud, dashboards).
  • The value of the data is in the moment — a fraud alert tomorrow is useless.
  • You need a safety net — replay and retention let you recover from processing errors.
Manager's readKafka is the backbone of "real-time" anything. When a business says "we need to react as it happens," a streaming tool like Kafka is underneath.
Block 3 · Cassandra

Cassandra

A database built to store enormous data across many machines and never go down — even when machines fail.

Cassandra · the everyday twin

The 24/7 store with many identical branches

Imagine a shop with dozens of identical branches, all stocked the same. If one branch closes, you walk to another and never even notice. There is no single "head office" that, if it shut, takes everything down.
  • Data is copied across many machines, so no single failure loses anything.
  • No single point of failure — every branch is equal; there is no fragile centre.
  • Always open: it keeps serving even during failures, upgrades, or huge spikes.
Cassandra · the ring and replication

Branches on a circular road

Picture the branches arranged around a ring road. Each item is assigned to the nearest branch based on its address — then automatically copied to the next two branches clockwise. No head office decides this; the ring itself is the rule.

The ring

Consistent hashing

Each row's partition key (e.g. customer_id) is hashed to a position on the ring. The node at that position owns the row. No central directory needed.

Replication factor

How many copies

RF = 3 is typical: every row lives on three nodes. Lose one? Two still have the data. Lose two? The third survives. Copies are automatic.

No boss node

Peer-to-peer

Every node is equal. Any node can accept a read or write. There is no master whose failure brings the system down — that is the whole magic.

₹ Why the CFO caresNeed to handle more traffic? Add more nodes to the ring. Cassandra automatically rebalances data across them — no downtime, no redesign. Linear scaling: double the nodes, double the capacity.
Cassandra · the real tradeoff

Speed vs. certainty — you choose

When checking stock at the branches — do you phone one branch (fast, but maybe they have not restocked yet), a majority (balanced), or all of them (certain, but slow — and it fails if even one branch is closed)?
Consistency levelWhat it meansSpeedRisk
ONEAsk one replica, trust its answerFastestMay read slightly stale data
QUORUMAsk a majority (2 of 3), take the latestBalancedSurvives one node down; most apps use this
ALLAsk every replica, all must agreeSlowest100% certain — but one node down kills the read
The manager's tradeoffMost production systems use QUORUM: fast enough, reliable enough, survives failures. Choosing ALL sounds safe but defeats the purpose — you have made the system as fragile as its weakest node. This is a business decision, not just a technical setting.
Cassandra · the key contrast

Hive answers big questions. Cassandra serves fast ones.

 Hive (last week)Cassandra
JobAnalyse — big questions over historyServe — millions of tiny live lookups
SpeedSlow, batch (seconds–minutes)Instant (milliseconds)
UptimeRuns when you askAlways on, never down

Don't mix them upHive is for understanding the business. Cassandra is for running it live. Different jobs, different tools.
Cassandra · who uses it & why

When "down" is not an option

  • Netflix — your viewing history and "continue watching," served instantly to millions, always available.
  • Instagram / Apple — massive volumes of user data that can never show an error page.
  • Facebook built Cassandra originally, for inbox search at enormous scale.
  • Anything where a few seconds of downtime = lost money or trust.
◆ Discuss
Why would a bank pay far more for "never goes down" than for "answers analysis questions quickly"?
Cassandra · designing the shelf for the question

Query-first modelling — build the shelf for the shopper

In a normal database, you design your tables first, then figure out how to query them. In Cassandra, you start with the question the app will ask — "Show me Ananya's recent orders" — and build the table backwards from that. It is like organising a shop shelf not by supplier, but by what the customer reaches for.

Traditional (SQL) thinking

"Let me normalise the data perfectly. I will figure out queries later."

Works when you do not know questions in advance — but slow at massive scale.

Cassandra thinking

"What will the app ask? Build the table exactly for that query — even if it duplicates data."

Disk is cheap; downtime is not. Duplication is fine if reads are instant.

The expensive mistakeTeams that bring SQL habits to Cassandra — normalised tables, lots of joins — get the worst of both worlds: slow reads AND complex code. The rule is simple: one table per query pattern. If the app asks two different questions, you store the data two different ways.
Cassandra · when to reach for it

Reach for Cassandra when…

  • You need to always be available — downtime is unacceptable.
  • The data is huge and must scale across many machines smoothly.
  • You do lots of fast reads and writes of specific records — not big analytical scans.
  • You know your access patterns up front — the questions the app will ask are predictable.
Manager's readCassandra is what you buy when "the service must never go down" is worth more than "I can ask clever questions." It is an availability decision.
