0–8 min · Where this came from

Spark wasn't built to add features. It was built to fix a specific pain.

Every tool in this course so far solved one bottleneck. Spark's bottleneck was speed on repeated, iterative work — exactly the work a business analyst does when testing scenarios.

2009

Researchers at UC Berkeley's AMPLab are running machine learning experiments on Hadoop MapReduce. Training a model means running the same computation dozens of times over the same data — and MapReduce writes to disk after every single pass. The lab builds Spark specifically to keep that data in memory between iterations.

2010

Spark is open-sourced. Early benchmarks show iterative jobs running 10–20× faster than the equivalent MapReduce pipeline.

2014

Spark becomes a top-level Apache project. The same year, it sets a world record for large-scale sorting — beating Hadoop's MapReduce on the same benchmark using far fewer machines.

Today

Spark is the default engine behind almost every modern "lakehouse" platform, Databricks included — the subject of Class 2.

Why this history matters for you Spark is not "Hadoop, but newer." It's a different answer to a narrower question: Hadoop MapReduce asked "how do we process data too big for one machine?" Spark asked "how do we do that and run the same job on the same data again and again without paying the disk-I/O tax every time?"
8–16 min · The business crisis

Why QuickKart needed something faster

The MapReduce problem

Every Map step, every Reduce step, every stage in a pipeline writes its result to disk before the next step can read it. Safe — the job survives a crash — but slow. Fine for a report that runs once, overnight. Punishing when Meera wants to try five scenarios in a row, each reusing the same base data.

The Spark idea

Keep the data in memory (RAM) across steps instead of writing to disk each time. The first read from HDFS is the only slow part — every transformation after that happens at memory speed, often 10–100× faster for iterative work.

Where this bites hardest

Machine learning training — the same dataset scanned dozens or hundreds of times to converge on a model.

Where this bites hardest

Interactive / exploratory analysis — an analyst asking "what about this filter instead?" every 30 seconds.

Where this bites hardest

Multi-step pipelines — clean → join → aggregate → join again, where MapReduce forces a disk round-trip at every arrow.

Everyday twin

MapReduce is a line cook who puts every half-finished dish back in the walk-in fridge, then takes it back out for the next step — even if the next step happens ten seconds later. Spark is the same cook keeping the pan on the stove, working through all the steps of one order before it ever needs to go back to storage.

Business value The discount-scenario test that took 5 hours across five MapReduce jobs now takes under 5 minutes on Spark, because the orders table is loaded into memory once and reused for all five what-if queries. That's the difference between Meera walking into her 9 AM meeting with numbers or with excuses.
The honest caveat In-memory only helps if the working data fits in the cluster's combined RAM — and only if you actually ask Spark to keep it there (more on this under caching). Spark doesn't make disk-bound, one-pass jobs dramatically faster; its advantage is concentrated in iterative and interactive work.
16–34 min · The architecture, properly

Three roles, and what each one actually holds

Every Spark job — however small — involves the same three players. Today we go one level deeper than "driver, manager, executor" into what each one is actually doing and holding in memory.

Driver Program

Runs your code. Holds the SparkSession (your entry point). Contains the DAG scheduler (splits the job into stages) and the task scheduler (hands individual tasks to executors). Collects final results when you call an action like .collect().

Cluster Manager

The resource broker — negotiates with the underlying infrastructure for machines, then hands the Driver a set of executors to work with. Doesn't touch your data at all; purely an allocator.

Executors

The actual workers, one process per node (usually). Each runs many tasks in parallel threads, and holds a slice of the data in its own memory — split further into storage memory (cached data) and execution memory (working space for shuffles and joins).

Cluster manager: three ways to get machines

Cluster managerWhat it isTypical setting
StandaloneSpark's own simple built-in manager — no other software needed.Small teams, learning, single-purpose Spark clusters.
YARNHadoop's resource manager — the same YARN from earlier sessions.Enterprises with an existing Hadoop cluster; Spark shares the same machines as Hive jobs.
KubernetesContainer-based scheduling — each executor runs as a pod.Cloud-native shops; this is what Databricks runs underneath.

Executor memory, split in two

Storage memory

Holds cached / persisted RDDs and DataFrames — the "keep this on the stove" memory from the caching demo.

Execution memory

Working space for active computation — shuffles, joins, sorts. If a job runs out of this, performance degrades sharply (spilling to disk) before it fails.

Everyday twin

The Driver is the head chef who reads the whole order ticket and decides the sequence of steps before anyone touches a pan — and keeps a runner (the task scheduler) sending instructions to each station. The Cluster Manager is the restaurant manager who assigns which line cooks are free tonight — they don't cook, they staff. Each Executor is a line cook with two counters: one for ingredients they're keeping prepped and ready (storage memory), one for the dish actively being assembled (execution memory).

One thing worth remembering A Spark job doesn't run on "the cluster" as one blob — it runs as many small tasks, typically one per data partition, spread across executors, all following the plan the Driver built. More partitions than executor cores means some tasks queue and wait their turn.

42–52 min · Spark concepts · Part 1

RDD — the idea everything else is built on

Resilient Distributed Dataset

A collection of records, split into partitions, spread across the executors' memory. Two properties matter more than the name: it's immutable (a transformation never changes the original, it produces a new RDD) and it's resilient — if a partition is lost when a machine dies, Spark doesn't need a backup copy of the data. It just replays the recipe that built that partition.

How an RDD actually gets created

From a collection already in memory
sc.parallelize(["a","b","c"])

Rare in practice — mostly used for teaching and testing.

From external storage
sc.textFile("/data/orders.csv")

The real path — HDFS, DBFS, or cloud storage. This is how QuickKart's orders actually enter Spark.

Persistence levels — where "cached" data actually lives

LevelWhere it's storedTrade-off
MEMORY_ONLYRAM only, as Java objectsFastest reuse. Lost partitions are recomputed if memory runs out.
MEMORY_AND_DISKRAM, spills to disk if it doesn't fitThe safe default — slower than pure memory, never forces a full recompute.
MEMORY_ONLY_SERRAM, serialized (compressed) formFits more data per GB of RAM, costs CPU time to compress/decompress.
DISK_ONLYDisk onlyFor data too big to ever fit in memory — still beats recomputing from source.

.cache() from the Hello World demo is just shorthand for .persist(MEMORY_ONLY).

Everyday twin

Every station's ingredients are labelled with the recipe steps that produced them, not just the ingredients themselves. If station 3's tray falls on the floor, nobody panics — you just re-read the recipe card (the lineage) and remake that one tray from the last known-good ingredients. And "persistence level" is just: do you keep the prepped tray on the counter (memory), move it to the walk-in when the counter's full (memory-and-disk), or straight into cold storage because there's no counter space at all (disk only)?

52–60 min · Spark concepts · Part 2

Transformations vs actions — and which ones cost a shuffle

Transformations

select, filter, groupBy, join — these describe a step but don't execute it. Spark just adds the step to the plan. This is lazy evaluation.

Actions

show(), count(), collect() — these trigger execution. Spark now looks at the whole plan built so far and runs it.

Not all transformations cost the same

Narrow transformations

Each output partition depends on exactly one input partition. No data has to move between executors. Examples: map, filter, union. Cheap — stays inside the same stage.

Wide transformations

Each output partition may depend on many input partitions, scattered across executors. Data has to be redistributed over the network — a shuffle. Examples: groupBy, join, distinct, repartition. Expensive — and this is exactly what creates a new stage, coming up next.

Everyday twin

Writing "chop onions, then sauté, then add tomatoes" on the order ticket is a transformation — nobody's cooking yet. Calling out "fire it!" is the action. Chopping and sautéing at your own station is narrow — you never need another station's tray. But "combine every station's tomato prep into one bowl before plating" is wide — someone has to physically walk trays between stations first. That walk is the shuffle, and it's the single most expensive thing that happens in a Spark job.

Why this is worth memorising Almost every real Spark performance problem traces back to too many unnecessary wide transformations — repeated shuffles that could have been combined into one. Reading the DAG (next) is how you actually see this happening instead of guessing.

Directed Acyclic Graph — every transformation you chain together becomes a node; data always flows one way, and the plan never loops back on itself. Now that you know narrow vs wide, here's the rule that turns a DAG into stages: a new stage begins every time there's a shuffle.

The hierarchy, top to bottom

LevelWhat it is
JobTriggered by one action — everything above, from "fire the order" down.
StageA chunk of the job with no internal shuffle. A new stage starts every time a wide transformation forces one.
TaskThe smallest unit of work — one stage, run on one partition. If you have 200 partitions, stage 1 launches 200 tasks, spread across however many executor cores are free.
Everyday twin

The ticket says: bring ingredients from the pantry, wash them, chop — that's Stage 1, and every station does it independently, in parallel, with zero coordination. Then: combine every station's chopped tomatoes into one bowl before the sauce step — that requires physically walking trays between stations, which only starts once every station has finished Stage 1. That handoff point is the shuffle, and it's exactly where Stage 2 begins.

Business value Because Spark sees the entire DAG before running anything, it can push the "festival week" filter down to happen before the shuffle — reading and moving less data in the first place. That optimisation is invisible to Meera; all she sees is her answer arriving in seconds instead of minutes.
Where you'll actually see this Every Spark cluster (including Databricks) ships a Spark UI with a visual DAG for every job you run — the exact stage/task breakdown above, with real timings. First thing we'll open in Class 2.
70–72 min · Quick self-test

Tap each term — do you have it?

Which is narrow and which is wide: df.filter(...) and df.groupBy(...)?
Tap to reveal
filter is narrow — each output partition only needs data already sitting in its matching input partition. groupBy is wide — rows with the same key can be scattered across every partition, so they all have to be shuffled together first.
A transformation like .filter() is called. Has any data actually been filtered yet?
Tap to reveal
No. Transformations are lazy — Spark only adds the step to the plan (the DAG). Nothing executes until an action like .show(), .count(), or .collect() is called.
A worker machine crashes mid-job. Does Spark need a backup copy of the lost partition to recover?
Tap to reveal
No. That's the "Resilient" in RDD — Spark keeps the lineage (the recipe of transformations) for every partition, and simply recomputes the lost one from its lineage.
A job's DAG has two shuffles in it. How many stages does it have?
Tap to reveal
Three. A new stage begins after every shuffle — so two shuffles split the job into three stages: everything before shuffle 1, everything between the two shuffles, everything after shuffle 2.
Which Spark component would you reach for to flag a fraudulent order the second it's placed, not in tomorrow's batch report?
Tap to reveal
Structured Streaming. Spark SQL and DataFrames are for batch analysis of data already at rest; Streaming treats the live order feed as a continuously growing table.
